fix: 隧道「假活」导致 Error 1033 —— 守护改为真实探测通不通

用户报 Error 1033（Cloudflare Tunnel error），并说「进入员工档案编辑再按
返回详情就出现」。该操作与报错无关：员工详情页只是普通页面，
问题在网络层 —— Cloudflare 连不到本机隧道。

根因：cloudflared 进程活着，但到 Cloudflare 的连接已断（zombie）
- tasklist：cloudflared.exe PID 22616 存在
- netstat ：该 PID 只有一条 127.0.0.1:20241 LISTENING，
  与 Cloudflare 的连接一条都没有
- 公网：http=000（连不上）；本机服务：http=200（Next.js 正常）
- 旧守护只查「进程在不在」→ 永远认为正常 → 隧道僵着不管

修复（scripts/autostart.mjs）
- probeTunnel(url)：用 fetch 真实请求 <url>/login；
  2xx/3xx/401 算通，5xx（尤其 Cloudflare 的 530/1033）算断
- killStrayCloudflared()：结束所有僵死 cloudflared 再重建
- ensureTunnel() 改造：进程没了→拉起；进程在但探不通→连续失败 2 次后杀掉重建
- 防抖：PROBE_MIN_INTERVAL=120s、FAILS_BEFORE_REBUILD=2，
  避免网络抖动导致地址反复变（第一版 90 秒/1 次会误判，实测连建 3 个隧道）

实测
- 杀 cloudflared → 自动重建 → 4 秒拿到地址 → 公网 200
- 模拟僵死（探测目标指向不存在的域名，进程照旧活着）
  → 日志出现「✗ 外网地址连续探不通…正在重建隧道…」→ 重建成功，公网恢复 200
- 回归 test:stage9 39/39 · test:stage8 18/18 · check:auth 43/43 · typecheck 通过

以后隧道断（任何原因）会在 2~5 分钟内自动重建，地址换新，
在「访问入口」页能看到当前地址。

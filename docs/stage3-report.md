### 2.2 门店别名模型 `StoreAlias`

```prisma
model StoreAlias {
  id      Int      @id @default(autoincrement())
  storeId Int
  alias   String   @unique   // 一个别名只能属于一家门店
  note    String?
  store   Store    @relation(..., onDelete: Cascade)
}
```

**为什么这样设计就能「不复制员工数据」：**

- 别名表只存「字符串 + 指向标准门店的外键」，**不含任何员工字段**；
- 登记别名时，把「门店原文列 `storeNameRaw` 等于该别名」的员工**重新挂到标准门店** —— 只改 `storeId` 一个外键；
- `storeNameRaw` 原文一律保留，随时可追溯，不做覆盖、不做物理迁移。

**统一归属的效果（实测）：**

| 场景 | 登记前 | 登记后 |
| --- | --- | --- |
| 用标准名「阶段三测试门店_临时」检索 | 1 人 | **2 人** |
| 用别名「阶段三测试_旧写法」检索 | 1 人（另一批人） | **2 人** |
| 两次返回的员工 id 集合 | 不同 | **完全一致** ✅ |
| 门店分布统计里该店人数 | 1 | **2，在职 2** ✅ |
| 员工总数 | — | 只 +2（即新增的 2 名测试员工，**零副本**） |

### 2.4 批量编辑 `/employees/batch`

| 环节 | 实现 |
| --- | --- |
| 筛选 | 快捷条件「部门为空 / 岗位为空 / 门店为空」+ 关键词 + 门店 / 部门 / 岗位 / 状态任意组合 |
| 预览 | 提交前先预览命中名单（与提交用的是**同一套参数，同一条查询**） |
| 范围 | 「全部命中」或「仅勾选」，避免误改 |
| 可改字段 | **只允许改 门店 / 部门 / 岗位**（服务层还有白名单兜底） |
| 留痕 | 逐条写 `EmployeeHistory`，来源 `BATCH_UPDATE`，同一次操作共享 `batchKey` |
| 二次确认 | 提交前弹窗明确显示「范围 + 修改内容」 |

**为什么只放开三个字段：** 在职状态、入职/离职日期、身份证与银行卡信息一旦被批量误改，
破坏面远超归属字段且难以察觉。因此这些字段只在单条编辑中修改，不参与批量。

### 2.5 员工变更记录 `EmployeeHistory`

```prisma
model EmployeeHistory {
  employeeId   Int
  employeeCode String?   // 业务编号快照（THHR…）
  batchKey     String?   // 同一次操作多字段归组
  source       String    // CREATE | UPDATE | BATCH_UPDATE | SOFT_DELETE | RESTORE
  fieldName    String    // 字段名
  fieldLabel   String?   // 字段中文名
  oldValue     String?   // 修改前（已脱敏）
  newValue     String?   // 修改后（已脱敏）
  operator     String    // 操作人
  operatedAt   DateTime
}
```

**自动记录范围：** 新增 · 单条编辑 · 批量修改 · 停用 · 恢复 —— 全部自动写入，无需人工操作。

设计要点：

1. **一个字段一行**，`batchKey` 把同一次操作归组；只写**真正变化**的字段（值相同不写）。
2. **敏感字段只记脱敏值**（身份证 / 银行卡 / 手机号 / 住址 / 薪资），与列表页口径一致 ——
   实测：把手机号改成 `13700137000`，历史里记录为 `137****7000`。
   避免「为治理数据而新建的表」变成新的泄露面。
3. **操作人**：当前未启用登录，取请求头 `x-operator`，缺省记为「系统（未启用登录）」。
   接入登录后改从会话取，前端无需改动。
4. 展示位置：员工详情页新增「变更记录」Tab，按时间倒序，含修改前 / 修改后 / 操作人 / 时间。

## 四、发现问题

### 4.1 已修复：`NOT: { storeId }` 静默漏掉「门店为空」的员工（本次发现并修掉的唯一缺陷）

写别名统一归属时，我最初用 `NOT: { storeId: x }` 筛选「尚未挂到标准门店的员工」。
Prisma 会把它翻译成 SQL `NOT (storeId = x)`，而 SQL 里 `NULL = x` 结果是 `NULL`，
`NOT NULL` 仍是 `NULL` → **整行被排除**。

也就是说：**`storeId` 为 NULL（门店为空）的员工永远不会被别名统一归属** —— 而这恰恰是这个功能最该处理的那批人。

验收测试直接抓到了它（「重挂 1 人」实测为 0）。修正为显式覆盖 NULL：

```ts
// ❌ 会漏掉 storeId 为 null 的行
NOT: { storeId: storeId }
// ✅
OR: [{ storeId: null }, { storeId: { not: storeId } }]
```

### 4.2 已修正：别名候选检测一开始检测错了对象

第一版把候选定义为「门店原文列 vs 门店名」，结果**候选为 0**。原因：这个数据集里同义写法
**各自都已成为独立的 Store 记录**（所以库里是 66 家而不是 52 家），原文列反而都能对上号。
改成**门店名之间两两比对**后，正确检测出 **16 组**。

### 4.3 业务侧问题（均来自 Excel 源数据，系统未自动修正）

1. **16 组门店是同一家店的两种写法**，66 家门店实际约 **50 家**。
   规律清晰：无「店」后缀的记录几乎全是离职（某典型组：0 在职 / 51 人），
   带后缀的多为在职（同一家店的另一种写法：14 在职 / 22 人）→ 高度疑似前者是历史写法。
   （具体门店名不在本文档列出，请在 `/stores` 页面的「别名候选」中查看。）
   影响：同一家店在门店查询与分布统计中被拆成两行，跨店统计（如流失率）会失真。
   **未自动合并**（属业务判断），已提供候选清单与「登记别名」的一键路径。
2. **1902 人（99%）无部门归属** —— Excel 只给了「运营部」，是数据完整率只有 0.9% 的主因。
   这是「批量编辑」存在的意义：按门店批量指定部门即可把完整率拉上去。
3. **状态冲突 14 人** 需 HR 逐人确认口径（明细页已关联到具体员工与 Excel 原始行号）。
4. **18 人身份证 / 手机 / 入职日期全为空**，无法判定是否与他人重复（重复风险最高的一类）。
5. **102 人 Excel「门店名称」本身为空**，既无门店也无部门，需补录来源才能归位。
6. 本阶段**没有自动修复按钮**：可批量修的三类走「批量编辑」，状态冲突需人工确认。

### 4.4 一个需要注意的行为

`EmployeeHistory` 外键是 `onDelete: Cascade`。员工走的是软删除（正常业务不会触发），
但 `cleanup-test-data.ts` 这类脚本**物理删除**员工时会连带删除其历史记录。
若将来需要对已删档案保留历史，应改为「软删除 + 归档」或在删档前把历史导出留档。
当前阶段可接受（员工一律软删除，硬删除只发生在测试清理）。

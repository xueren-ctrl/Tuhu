## 三、Cluster-16 专项确认（用户重点关注项）

### 结论：确认成立，且属于指令中的「情况 A」

| 项目 | 事实 |
|---|---|
| `惠州水云居` | Store **#383**，ACTIVE，33 人（在职 0 / 离职 33） |
| `惠州水云居店` | Store **#384**，ACTIVE，7 人（在职 0 / 离职 7） |
| `惠州水北新村店` | Store **#385**，ACTIVE，**已存在于生产库**，11 人（在职 7 / 离职 4） |
| Excel「在职」B123~B129 | 7 行均为 `惠州水北新村店` |
| Excel 全文检索 | `惠州水云居` / `惠州水云居店` **在「在职」「南昌3店」中均 0 命中**（仅在「数据库」历史 Sheet 出现） |
| 交叉验证 | Excel「在职」中 `惠州水北新村店` = 7 行，与库中 #385 的 **7 名在职员工完全吻合** |

→ 证据链：两个旧名均为**历史名称**；当前真实标准名称为 **`惠州水北新村店`**；
   该名称在生产库中**已存在 ACTIVE Store（#385）**，且其在职人数与 Excel 完全一致。

### ⚠️ 执行阻塞点（需人工决策，本阶段不自行处理）

现有 `mergeStores()` 的第 ⑧ 项校验要求：`mainStoreId + mergeStoreIds` 必须**全部属于同一个
当前 `findMergeClusters()` 候选簇**，否则抛 `InvalidMergeClusterError` → 409 `INVALID_MERGE_CLUSTER`。

实测：**#385 不在 #383/#384 所在的候选簇内**（该簇只含 383、384）。
因为 385「惠州水北新村店」与 383/384「惠州水云居(店)」在名称上不满足现有候选规则。

因此，若直接把 383/384 合并到 385，**现有接口会直接拒绝**。可选处理方向（均需你确认后另行开发，
本阶段绝不擅自修改候选算法或绕过校验）：

1. 为「历史改名合并」新增独立的执行路径（携带 `canonicalName` + `canonicalSource` + 改名证据），
   不受同名候选簇约束，但仍走 preview → confirm → 事务执行 → 验收。
2. 扩展候选算法，让「已存在 ACTIVE 标准门店 + 显式历史名称映射」构成一个合法合并簇。
3. 暂缓 Cluster-16，先处理 Cluster-01~15。

## 二、完成模块

### 2.1 门店合并 `/stores/merge`

把疑似同一家店的多条门店记录合并到一条「主门店」名下。当前检测到 **16 组**候选（两两相似门店经并查集聚成的簇）。

需求书四条硬要求的落实方式：

| 要求 | 实现 |
| --- | --- |
| ① 只修改 `Employee.storeId` | 迁移时 `update({ data: { storeId } })`，**只改这一个外键** |
| ② 禁止删除员工数据 | 一行都不删；被合并的门店记录也只置 `status=INACTIVE`，不删除（可回退） |
| ③ 保留 `StoreAlias` 记录 | 被合并的门店名自动登记为主门店的别名，历史写法不丢 |
| ④ 生成 `EmployeeHistory` | 每迁移一名员工写一条变更记录（来源 `BATCH_UPDATE`，同批次共享 `batchKey`） |

另外还顺带处理了「门店原文列仍写着旧名、但外键没挂上」的散落员工，同样只改外键。

**实测：** A 店 2 人 + B 店 1 人 → 合并后主门店 3 人（= 2+1），B 店归零，**员工总数 1923 不变（零删除）**；
用被合并门店名检索仍能查到该批员工（别名生效）。

### 2.2 部门自动归属 `/employees/department-auto` + `DepartmentRule`

新增 `DepartmentRule` 模型，按三个维度描述「什么样的人归到哪个部门」：

| 维度 | 字段 | 说明 |
| --- | --- | --- |
| 门店 | `storeId` | 精确匹配，留空=不限 |
| 岗位 | `positionId` | 精确匹配，留空=不限 |
| 员工类型 | `employeeType` | ⚠️ 源数据无独立字段，按「工种级别原文包含」匹配 |

已填维度之间是 AND；`priority` 越小越优先；一名员工命中多条时取优先级最高的。

流程：**配置规则 → 预览「将修改多少员工」→ 确认后批量更新**。预览是只读的，可反复点；
执行走标准的批量更新路径，因此自带变更记录。

⚠️ 关于「员工类型」的诚实说明：源数据里**没有独立的员工类型字段**，
所以这一维是用工种原文做的文本匹配（填「店长」可命中「技术店长」「副店长」）。
这一点在页面上明确标注，避免误以为源数据真有该字段。若确实需要，应先在源数据补这一列。

**实测：** 预览「将修改 3 人」→ 执行后实际修改 3 人（一致）；部门统计 `0 → 3`，未分配 `1905 → 1902`。

### 2.3 数据质量中心升级（新增 `QualityIssue`）

从「只展示问题」升级为「有处理流程」：

```prisma
model QualityIssue {
  issueType    String   // 与数据质量类别 key 一致
  employeeId   Int
  employeeCode String?  // 业务编号快照
  status       String   // OPEN 待处理 | CLOSED 已关闭 | IGNORED 已忽略
  handler      String?  // 处理人
  handledAt    DateTime?// 处理时间
  result       String?  // 处理结果说明
  @@unique([issueType, employeeId])
}
```

设计要点：

1. **`(issueType, employeeId)` 唯一** —— 同一员工同一类问题只有一张工单，重复点是幂等 upsert。
2. **关闭必须填处理结果说明** —— 否则后人看到「已关闭」却不知道为什么关，等于把问题藏起来。
3. **口径：待处理 = 检出总数 −（已关闭 + 已忽略）**。
   注意**检出总数不会变** —— 关闭是「人工确认这条不用管了」，不等于数据变好了，
   两个数字都展示，避免自欺欺人。
4. 明细页每条问题都有「关闭 / 忽略 / 重新打开」按钮，中心页新增「待处理 / 已处理」双指标。
5. 中心页新增「处理入口」区块，把五类问题直接指向对应的解决工具。

**实测：** 关闭 1 条「无岗位」问题 → 待处理 `39 → 38`、已处理 `0 → 1`、**检出总数 39 不变**；
重新打开后统计回滚。

### 2.4 Excel 重新导入预览 `/import`

流程固定：**上传 → 解析 → 生成 Diff → 人工确认 → 才写入**，明确禁止「上传即覆盖」。

| 环节 | 实现 |
| --- | --- |
| 表头校验 | 校验 6 个关键列的表头文字，列顺序被改动过就直接拒绝（避免身份证号错位写进银行卡列） |
| 匹配 | 复用导入脚本的同一套去重级联（身份证+入职日期 → 身份证唯一+无入职日期 → 姓名+入职日期 → 姓名+电话 → 溯源行号） |
| Diff | 逐字段列出「修改前 → 修改后」，并单独统计状态变化 / 门店变化 / 岗位变化 / 新增 |
| 落盘 | 原文件存到 `data/import/`，确认时基于**同一份文件重新解析**再写入，保证「所见即所写」 |
| 防重复 | 批次状态机 `PENDING → COMMITTED / DISCARDED`，已处理批次不能再次提交 |
| 留痕 | 写入走 `updateEmployee` / `createEmployee`，自带变更记录 |

**实测（验收点）：** 上传当前源文件 → Diff 生成完毕 → **员工总数与变更记录数均未变化**；
造一个改了门店的文件上传 → 正确识别出门店变化 → **数据库依然零变化**；
丢弃该批次后再次提交被拒绝（防重复写入）。

## 四、发现问题

### 4.1 已修复：预览解析器与导入脚本口径不一致（最严重，验收时暴露）

第一次把**当前源文件**重新上传做预览时，Diff 竟然显示 **364 处待修改**。
按理说数据库就是从这个文件导入的，差异应该接近 0 —— 这说明解析器有偏差。
逐条拆解后定位到三个真实缺陷，**每一个都会在确认写入时改坏数据**：

| 缺陷 | 影响 | 修复 |
| --- | --- | --- |
| **状态判定漏了「离职」名册交叉比对** | 把 **171 人**从「离职」判成「在职」（正是那 14 个状态冲突者的同类），确认后会把大批离职员工错误改回在职 | 移植导入脚本的口径：离职信号 = 在「离职」名册 / 有离职日期 / 有离职原因 / 文本含离职字样，「重新入职」类文本不算 |
| **合并单元格未做防护** | ExcelJS 把合并主格的值回传给区域内每一格，于是「南昌3店」「运营部」这类**分节标题行**被读成姓名=门店=身份证=同一串字的假员工，产生 **4 条虚假新增** | 非主格的合并单元格一律视为空（与第一阶段导入脚本同一判据） |
| **身份证 / 手机 / 银行卡未归一化** | 大小写、分隔符造成 **374 处假差异**（如 `311X` vs `311x`） | 比较前统一：身份证转大写、手机与银行卡取纯数字；另补 Excel 数字序列日期的解析 |

修复后重传同一份源文件：**新增 4 → 0、状态变化 171 → 8、有效行 1938 → 1934、跳过 60 行** ——
行级结果与导入脚本**完全一致**。

### 4.2 仍未完全对齐：历史脏数据行的差异（本次未修，已在界面显著提示）

修复后仍有 **210 条**待修改差异，逐条核对后确认集中在三类历史脏数据行：

- Excel 里**身份证号 / 联系电话列错位**的行（导入脚本做过「按内容识别 + 安全归位」）；
- **离职日期写成文本**的行（如「2026年8月8日」、数字序列）；
- **门店 / 岗位名称被手工改写过**的行。

这些导入时都由脚本按各自的规则处理过并写入了导入报告，而预览解析器是独立实现，
**没有复刻这些特例处理**。

**处置**：
1. 页面上已加显著警告，列明这三类情况，要求逐条核对后再确认写入；
2. 报告中如实记录，**不掩盖**；
3. 若只是要修正归属类字段，建议改用「批量编辑」或「部门自动归属」—— 它们的口径是确定的。
4. 根治方案见「下一阶段建议」第 1 条。

# Tuhu 数据规则（2026-11-26，用户定）

> 原文件为准。导入什么样，导出就什么样；只有实时字段按系统实时重算。

## 1. 数据库表是唯一数据源

- 导入只读「数据库」表（45 列）。其他表（在职、离职、运营部、运营部离职、南昌3店、社保总名单、薪资表、招聘面试登记表等）不读，它们是公式引用数据库的展示。
- 原文件里各表用 XLOOKUP 按「姓名 + 入职时间」取数据库第一条（例：运营部第 8 行）。导出按同样口径从库里取数回填，显示的就是正确的数据。

## 2. 数据库只是一个数据库

- 数据库里的记录原样存、原样出。不合并、不删除、不猜。
- 没被任何表引用的数据库行，是当时新增的、没用上的记录，只存在于数据库里，不用管。
- 个案：刘超勇数据库 64 / 2072 两条在职记录（运营部、区域经理、2024-09-22 入职）都保留；运营部第 8 行引用的是 64 行；2072 行未被任何表引用，仅存于数据库。

## 3. 导入什么样，导出就什么样

- 静态字段原样：姓名、身份证、电话、门店、工种级别、协议勾选项、银行卡等，导出与原文件一致。
- 只有实时字段按系统实时重算：是否满 7 天、是否满 2 个月、在职年限、人员流失率（按导出当月）。
- 身份证 / 电话互换的行，导入时按内容归位，导出写回正确列（原文件本身是错位的，导出是纠正后的正确位置）。
- 电话不是合法手机号时保留原文（如「做了3天就走了」），不切数字。
- 招聘面试登记表、薪资表不重算，原样镜像。

## 4. 匹配与对齐（代码层面）

- 导入匹配：源行号优先 → 身份证 + 入职日期 → 身份证 → 姓名 + 入职日期（身份证冲突时拒绝）→ 姓名 + 电话（双方都无身份证且唯一候选时才用）。身份证不同，绝不按姓名合并。
- 导出对齐：源行号 1:1 → 身份证 → 入职日期（唯一才用）→ 电话（唯一才用）→ 首个不冲突的。身份证冲突绝不取。
- 冲突绝不猜：对不上唯一记录时跳过并留痕，不写错数据。
- `[object Object]` 一律写空（旧导入错位写进库里的脏值，导出不再原样输出）。

## 5. 红线

- 原文件只读，永不改写。
- 历史脏数据不擅自修正；要改先问用户。
- 修复脚本禁止写 `/root/Tuhu/` 和迁移备份库；先在副本上修，验证通过再换库。

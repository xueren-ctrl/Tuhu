# Stage 9 —— 员工表由状态驱动 + 新增员工 + 更改状态

> 完成时间：2026-09-26
> 目标：① 各「表」（在职/离职/南昌3店/运营部/招聘面试登记表/运营部离职/薪资表/数据库）
> 改为**由员工数据实时生成**；② 员工状态决定出现在哪些表；③ 提供「新增员工」「更改状态」两个操作。

## 一、状态 ↔ 表 对应关系（用户确认，不可自行改动）

| 状态 | 出现在哪些表 |
| --- | --- |
| 候选中 | **不出现在任何表** |
| 已面试 | 招聘面试登记表 |
| 已入职 | 在职 · 招聘面试登记表 · 薪资表 |
| 离职 | 离职 · 招聘面试登记表 · 薪资表 |
| 南昌3店 | 南昌3店 · 招聘面试登记表 · 薪资表 |
| 运营部 | 运营部 · 招聘面试登记表 · 薪资表 |
| 运营部离职 | 运营部离职 · 招聘面试登记表 · 薪资表 |
| 其他 | 其他 |

「数据库」**不受状态限制**，包含全部员工（也是唯一能看到「候选中」人的地方）。

改状态的本质就是让这个人「搬家」：离开旧表、进入新表，各表人数随之实时变化。

### 例外：招聘面试登记表 / 薪资表 以原始名单为准

这两张表**不是**按状态全塞，而是 **以导入时的 Excel 原始名单为准**，
只把「在软件里新增的员工」按状态规则追加在后面（用户 2026-09-26 明确要求：
人数要和原来一样；历史缺失的面试 / 薪资数据不回补；新增规则只对以后新增的人适用）。

实测这两张表本来就是「2026 年的名单」：招聘面试登记表 478 行的面试时间**全部**是 2026 年；
薪资表 290 行的入职时间**全部**是 2026 年。靠「有没有面试 / 薪资字段」去判定会对不上
（薪资字段有 1335 人有值，远超 290），所以只能保留原始名单归属。

实现见 `lib/sheet-fields.ts` 的 `SHEET_BASE`：

| 表 | 底座 | 说明 |
| --- | --- | --- |
| 在职 / 离职 / 南昌3店 / 运营部 / 运营部离职 / 数据库 | `employee` | 完全由员工数据生成 |
| 招聘面试登记表 / 薪资表 | `excel` | Excel 原始名单（478 / 290）+ 软件新增的员工 |

### 原始名单行的「状态」怎么来（Stage 9.2）

原始名单行本来没有状态。解决办法是把每一行**挂到员工档案上**（新表 `SheetRowEmployeeLink`），
挂上之后状态列显示的是这个人**现在**的真实状态，并能从行详情直接打开档案去改。

匹配规则（**只在唯一命中时才建关联，有歧义宁可留空，绝不猜**）：

| 方式 | 说明 | 命中 |
| --- | --- | --- |
| `pair` | 姓名 + 电话 在员工表唯一 | 396 |
| `pairTime` | 姓名 + 电话命中多人时，再用「面试时间」唯一筛一次 | 40 |
| `phone` | 电话唯一 | 1 |
| `nameHire` | 姓名 + 入职日期 唯一 | 283 |
| `name` | 姓名唯一 | 24 |
| | **合计** | **744** |

结果：招聘面试登记表 478 行挂上 **458** 行（剩 10 行有歧义、10 人在员工库里根本没有档案）；
薪资表 290 行挂上 **286** 行（剩 4 人在员工库里没有档案）。
未挂上的行，状态列显示「**未建档**」并说明原因，点开也会明确提示「系统里没有对应档案」。

> 库里没有档案的多是「只来面试没有入职」的人 —— 他们本来就不该出现在其他表里，
> 留在这两张名单表里正好对得上原来的行数。

**「之前的员工要离职」怎么操作**（已做端到端验收，见 S9-04e）：

1. 在「更改员工状态」页（或该员工详情页）把状态改成**离职**
2. 他**自动从「在职」表移到「离职」表**（人数 290→289、1401→1402）
3. 他在「招聘面试登记表」「薪资表」里**那一行的状态列会同步变成「离职」**（原来显示「已入职」）
4. 「数据库」表不变（全部员工都在）
5. 改动全部写入变更历史与审计

## 二、各表怎么生成

```
Employee 表（唯一数据源）
   │  ① 按状态筛选（statusesForSheet）
   │  ② 按该表的列清单逐格取值（SHEET_COLUMNS）
   ▼
/sheets/<表>      实时生成、可增删改
/excel/<表>       导入时的原样镜像，只读留档，用于对照
```

**关键点：列名不等于字段名。** 同一份数据在不同表里叫法不同，例如：

| 数据 | 在职 / 南昌3店 | 离职 | 运营部 | 数据库 |
| --- | --- | --- | --- | --- |
| `bankBranch` | 工资卡的开户银行支行 | 开户行 | 开户行 | 工资卡的开户银行支行 |
| `currentAddress` | 现居住地址 | 居住地址 | （户籍地址是另一字段） | 现居住地址 |
| `socialInsurancePurchased` | 社保购买 | 社保购买 | 是否买社保 | 社保购买 |

所以每张表的每一列都显式声明了「取自哪个员工字段」（`lib/sheet-fields.ts`），
列名与顺序仍与 Excel 该 Sheet 一致。

**计算列**（不落库、实时算）：序号、在职年限 / 在职期限、是否满7天、是否入职满2个月、
门店名称、工种级别、年龄、状态。

> ⚠️ 运营部 Sheet 原表有两列都叫「紧急联系人（电话）」，实际一列是联系人、一列是电话，
> 这里按真实含义分别命名为「紧急联系人」「紧急联系人电话」（数据不错位）。
> 「状态」列是系统加的（Excel 里没有），不需要时可在右上角「列」里隐藏。

## 八、已知限制

1. 各表的行数会随状态变化，**不再与 Excel 逐行一致**——这是本阶段的设计目标；
2. 「招聘面试登记表」「薪资表」以 Excel 原始名单为准（478 / 290），只追加软件新增的员工；
   历史缺失的面试 / 薪资数据按用户要求不回补。原始名单行的「状态」列留空。
3. 批量改状态一次最多 2000 人；已成功的保持生效（可断点续做），失败项逐条返回。
4. 同名员工允许存在（历史数据里本就有重复入职），新增时不做重复检测。
5. 离职 1401 vs Excel 1407、运营部离职 10 vs 9 的少量差异来自历史数据本身，
   已在「迁移结果」表中逐项列明，可用「改状态」逐个校正。

## 十、在哪里改员工信息（2026-09-26 补充）

### 一句话结论

**所有员工驱动的表，每一格都是从员工档案实时取值 —— 在任何一张表里改，
这个员工出现的所有表同时更新，不用手动刷新、不用逐张表去改。**

### 四个入口

| 想做的事 | 入口 | 适合什么场景 |
| --- | --- | --- |
| 改 7 个「是否」字段 | **任意员工表里直接点下拉**（是否住宿舍 / 社保购买 / 劳动合同 / 社保协议 / 消防承诺书 / 宿舍免责协议 / 入职体检） | 高频、只改一两个勾选项 |
| 改单个员工的全部资料 | **点该行 → 右侧详情 → 「打开员工档案 / 修改资料」** | 改电话、地址、银行卡、日期等 |
| 改一批人的同一字段 | **批量编辑**（门店 / 部门 / 职位） | 批量调岗、批量归属 |
| 改状态（决定出现在哪些表） | **更改员工状态**（批量）或档案页顶部（单个） | 入职 / 离职 / 转运营部 |

### 同步范围

以「陈增（THHR2026000001，已入职）」为例，把「是否住宿舍」从「否」改成「是」：

| 表 | 同步结果 |
| --- | --- |
| 在职 | 否 → **是** ✓ |
| 数据库 | 否 → **是** ✓ |
| 招聘面试登记表 | 这张表**本来就没有**「是否」列（底座是 Excel 原始名单）；它的「状态」列读员工档案，改状态同样同步 |
| 薪资表 | 同上 |

**规则**：该员工出现在几张表里，就同步几张；不在的表不受影响，也不该受影响。
